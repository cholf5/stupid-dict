# 发音方案评估：要不要换 Kokoro TTS

日期：2026-10-08

## 背景与目标

评估发音链路是否应该改用 Kokoro 这类小型神经 TTS 模型。触发问题是：
现在的 Piper 音质一般（清晰但机械），冷门词又落在系统 TTS 兜底上
（Linux 的 espeak 很难听），Kokoro（82M，开源 TTS 里质量口碑最好的一档）
看起来两头都能救。**这是一份评估决策文档，没有代码改动。**

## 现状盘点

- **构建期**：`AudioPackBuilder/Program.cs` 用 Piper（UK `en_GB-alan-medium`
  / US `en_US-lessac-medium`）给按词频选出的常用词（约 5.8 万词，`--top 80000`
  经 freq/bnc/考纲 tag 筛选 + 纯字母词过滤）逐词起进程生成 MP3，
  单声道 48kbps，约 116k 个文件、~2 小时，包体积 500MB 量级。
- **运行时**：`SpeechPlayback.Create` 两条腿——`AudioPackPlayer` 按词名找
  MP3 用平台文件播放器直放（macOS afplay / Windows MCI / Linux 播放器），
  没有该词回退 `SystemTtsPlayer`（macOS `say` 按口音挑 Daniel/Samantha、
  Windows System.Speech、Linux espeak-ng）。
- 该设计的真实优点：点击到出声 ~50ms、零运行时算力、App 包无 native 依赖、
  包走现成的镜像/断点续传/sha256 下载链、覆盖缺口是设计好的优雅降级。
  弱点只有两个：Piper 音质一般；尾部词落在系统 TTS，Linux 兜底最难听。

## Kokoro 事实（2026-10-08 核实）

- 82M 参数；kokoro-onnx 发布 fp32 ~300MB、int8 量化 ~80MB；Apache-2.0，
  生成音频可再分发。CPU 接近实时（官方口径 M1），单词合成亚秒级。
- **不比现在的引擎小**：Piper medium 模型 ~63MB，Kokoro 量化后 ~80MB，
  同一量级。它的卖点是"同尺寸下质量高得多"，不是小。
- 声线质量分布对本应用关键（VOICES.md 官方自评）：美音有 A 档
  （`af_heart` A、`af_bella` A-）；**英音最高只有 B-（`bf_emma`），
  其余 bf_/bm_ 多为 C/D**。UK/US 并列的应用换过去，美音明显提升，
  英音未必比现在的 `alan` 强，需试听对比。
- G2P 官方推荐 misaki（Python）。C# 运行时存在第三方移植
  `Lyrcaxis/KokoroSharp`（247★，活跃维护，NuGet 即插即用），
  依赖链与音素化方案需审查才能用于生产。

## 评估过什么

**A. 构建期换引擎**（Piper → Kokoro，产物仍是同样的 MP3 包）：
播放链、下载链、App 代码全部不动，包体积不变量级。主要工程量在
`Program.cs` 现在是逐词起 `piper` 进程，Kokoro 没有等价轻量 CLI，
要改成常驻 Python worker 批量读词表（几十行）；已发布用户要重下
500MB 包才能受益（可以不强制，manifest 有模型名字段可区分新旧包）。
风险接近零。

**B. 运行时内置模型**（App 内按需合成，替代整条链）：
收益是全词覆盖 + 下载反而变小（~80MB vs 500MB）。代价：
三平台捆绑 onnxruntime native（每 rid ~20-60MB）、G2P 依赖第三方移植、
常驻百 MB 级内存，且**延迟画像和词典使用模式恰好相反**——用户点的是
不认识的词，首点永远是 ~0.5-1.5s 的合成等待（落盘缓存可做到"合成一次
永久秒播"，但每个生词的第一次都是慢的），对比现在点 MP3 的 50ms。
还为"听一个词"这个窄场景引入一整条模型下载/推理/缓存代码面，
与"傻瓜词典"定位相抵触。它最大的收益象限是"冷门词 + Linux"——
占比最小、现在也"能用"的那块。**不做。**

**C. 缩包 + 运行时模型兜底**：两头都背（500MB 包 + 模型 + 两套代码），
不用考虑。**不做。**

**D. Piper 原地升档**（medium → high 档模型）：构建命令改一行，
音质小幅提升，成本近零。作为 A 的对照项先试听。

## 结论

现在不动。对"听清一个词怎么读"，Piper medium 已过可用线，Kokoro 是
打磨不是能力升级，而打磨的成本是一次 116k 文件的重建。当前架构
（预生成包 + 系统兜底）对单词发音这个窄场景本来就是对的。

**重开这个决策的触发条件**：
1. 用户反馈集中在音质难听（而非功能）→ 走 A，先做试听对比（见下）；
2. 用户反馈集中在冷门词兜底难听（尤其 Linux）→ 走 B 的窄版：
   int8 模型 + 合成落盘缓存，只作为兜底增强，不替换预生成包。

**若走 A 的试听清单**（先对比再决定重建）：US `af_heart`/`af_bella`
vs 现 `lessac`；UK `bf_emma` vs 现 `alan`（英音可能不换，双引擎分口音
可接受）；外加 D 项 piper high 作基线。构建侧注意：Kokoro 输出 24kHz、
需经 ffmpeg 转同样的 48kbps 单声道 MP3，包格式与 manifest 不变。

## 已知取舍

- 本文档只留决策痕迹，不改任何代码；下次触发时从「试听清单」直接开工。
- Kokoro 声线质量等级是模型作者自评，且英音档位数据量级低于美音，
  换引擎的英音收益结论以试听为准。
- A 方案的包内容变化对老用户不可见（不强制重下）；若未来要强制，
  需要包版本号机制，现在没有，届时是 A 的一小步增量。
