# 下载流程修复：两遍进度条、误报下载失败、全有或全无解压

日期：2026-10-08

## 背景与症状

首次下载词典/发音包时观察到三个问题：

1. 进度条满了之后又跑一遍，两遍的提示都是「正在下载」，看起来像
   「下载 + 解压」但解压不该提示下载。
2. 第二遍跑完后提示「下载失败」——但第一遍那么慢，下载本身肯定成功了，
   怀疑是解压失败被全盘归因为下载失败。
3. 词典和发音包两个下载都出现同样现象。

## 排查结论（实测）

- 从干净状态用真实 `AssetDownloadService` 跑完整链路（下载 173MB →
  sha256 → 解压 574MB），64 秒全过：**代码主链路本身是通的**。
- 当天 GitHub 直连间歇性完全不通（curl code=000），三个镜像
  （ghfast.top / gh-proxy.com / ghproxy.net）存活且 Range/206 正常、
  内容为真 zip；直连可用时尾段明显降速（144→160MB 花 19s，
  最后 13MB 花近 30s）——长传输尾段被掐是常态。
- 顺带排除了一个假设：`HttpClient` 默认 100s 超时在
  `ResponseHeadersRead` 下**不会**掐断响应体读取（本地慢速服务器实测），
  `FirstByteTimeout` 的设计成立。

因此现象的机理是：

- **两遍进度条 = 下载被断一次**。第一遍是慢源（直连超时/被限速的
  免费镜像），临近结尾断掉；第二遍是回退链里的下一个源从 `.part`
  断点续传，很快填满。两遍的标签都是「正在下载」——用户自然把
  第二遍误读成解压。
- **「下载失败」= 校验/解压失败被统一文案吞了**。下载、校验、解压
  任何一步失败都显示「下载失败：…」。而断点续传有一个固有风险：
  `.part` 残留自旧版本资产（或已损坏）时，续传会把两段不同来源的
  字节拼成 frankenfile，只有 sha256 校验能发现——于是表现为
  「下载明明跑完了，却报下载失败」。更糟的是旧代码校验失败后
  **并不删除**损坏文件（`ChecksumFailed` 文案声称「已删除」但没人删），
  损坏的 `.part`/zip 留在临时目录里继续毒化下一次重试。

## 改了什么

- **阶段化失败文案**（MainWindow）：下载失败、校验失败
  （`ChecksumFailed`，自解释）、解压失败（`ExtractFailedFormat` /
  `AudioPackExtractFailedFormat`）分开。新增
  `AssetBootstrapException`（`Assets/`）：下载/校验阶段的异常在
  抛出点就带上最终用户文案，顶层 catch 原样展示，不做二次包装。
- **校验失败自动恢复**（`MainWindow.DownloadAndVerifyAsync`，两个
  下载流共用）：校验失败 → 删除 zip 与 `.part`（让「已删除损坏文件」
  成为真话）→ 显示「校验失败，已删除损坏文件，正在重新下载…」→
  从零重下一次 → 再失败才把 `ChecksumFailed` 报给用户。污染性
  frankenfile 从「必然反复失败」变成一次自愈。
- **续传标签**（`DownloadProgress.ResumedFromBytes`）：某次尝试从
  `.part` 起点续传时，进度行显示「断点续传 X / Y MB」而不是
  「正在下载」，第二遍进度条自解释。
- **解压真正全有或全无**（`ExtractZip`）：先解压到目标目录内的
  `.stupiddict-extracting-*` staging 目录，成功后逐条目同卷 rename
  进位（`MoveIntoPlace`，覆盖语义与原 `overwriteFiles: true` 一致），
  finally 清 staging；进入前清扫崩溃残留的 staging 目录。兑现
  AGENTS.md 里「半解压的发音包会因 uk/ 目录存在被误判为已安装」的
  承诺——解压中途失败（磁盘/CRC/中断）不再留下半套发音包。

## 评估过、决定不做

- **给 `.part` 记来源指纹（sidecar 文件）**：能提前拦住跨版本续传，
  但校验 + 自动重下已经把后果兜住，多一份状态文件多一份清理负担。
- **镜像顺序洗牌 / 把坏镜像从代码里换掉**：当天实测三个镜像都健康，
  问题不在镜像本身；镜像列表本来就是代码，死了随时可换。
- **校验失败重试多次/换镜像重试**：一次足够把脏状态清掉；连续失败
  说明是系统性问题（镜像坏了/资产被改），该让用户看到失败而不是
  静默空转。
- **消除下载阶段本身的两遍进度条**（例如合成多个源为一个进度）：
  续传进度对用户是有用信息（在哪个源续、传到多少），标签区分开
  即可，没必要隐藏。

## 测试

`tests/StupidDict.App.Tests/DownloadFlowTests.cs`（5 个）：

- 校验失败清残留并自动重下一次成功（重试前目标文件必须不存在）。
- 连续两次校验失败：状态行显示 `ChecksumFailed` 文案、按钮恢复、
  目标文件与 `.part` 均被清除。
- 续传尝试的状态行带「断点续传」。
- 损坏 zip 解压失败后目标目录原样（无条目、无 staging 残留）；
  损坏手法是解析 local header 后把 deflate 首字节 BTYPE 置为
  保留值 11（stored 条目 .NET 不校验 CRC，不能靠翻字节）。
- 含 uk/+us/ 两个顶层目录的包覆盖旧条目并清扫残留 staging
  （发音包真实形态，防止「边遍历边移动」竞态回归）。
